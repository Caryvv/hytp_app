# 01 系统总体架构

## 1. 整体架构

「汉韵同袍」是一个「工具 + 交易 + 社交 + 文化」四位一体的汉服生态平台，采用**多端 + 单一后端 API + 独立 AI 服务**的架构。

│  Compose)    │   │              │   │              │
└──────┬──────┘   └──────┬───────┘   └──────┬───────┘

## 2. 后端分入口设计（Yii2 advanced）

Yii2 advanced 模板天然支持多应用，规划三个入口应用，共享 `common`（模型、DB、业务服务）：

| 应用目录 | 面向 | 域名示例 | 鉴权 |
|----------|------|----------|------|
| `api/` | 用户端 App | `api.hytp.com` | JWT（用户） |
| `merchant/` | 商家端 SaaS | `merchant.hytp.com` | JWT（商家账号） |
| `admin/` | 管理员端 | `admin.hytp.com` | JWT（后台 RBAC） |
| `common/` | 三端共享 | — | 模型/服务/DB 配置 |

三端复用同一套 `common\models`（ActiveRecord）与 `common\services`（业务逻辑层），避免逻辑重复。控制器只做参数校验与响应拼装，业务写在 Service 层。

## 3. 分层约定（后端）

```
common/
  models/       ActiveRecord，一表一模型
  services/     业务逻辑（UserService、OrderService、TryOnService...）
  dto/          入参/出参数据结构
  enums/        枚举（订单状态、商品类型、形制朝代...）
  helpers/      工具
api/
  controllers/  用户端控制器（瘦控制器）
  modules/      按业务模块分（shop、social、travel、culture、learn）
```

- **控制器**：参数校验（Yii Model rules / DTO 校验）→ 调 Service → 返回统一响应。
- **Service**：事务边界、业务规则、跨表操作、调用 AI 服务、写操作日志。
- **Model**：数据映射、关系（hasMany/hasOne）、基础校验、scenario。

## 5. 关键技术选型说明

- **鉴权**：JWT（`Authorization: Bearer <token>`），Access Token 2h + Refresh Token 30d，Refresh 存 Redis。三端用不同的签发 `aud`，互不通用。
- **缓存**：Redis 缓存首页推荐、形制科普、商品详情等热点；社交 Feed 用 Redis List/ZSet 做时间线。
- **文件**：客户端直传 OSS（后端签发 STS 临时凭证），DB 只存 URL/key，避免大流量过后端。
- **AI 服务**：Python FastAPI 独立部署，Yii2 通过内网 HTTP + 内部签名调用；耗时任务（试穿渲染）走队列异步，客户端轮询/推送获取结果。
- **消息推送**：极光/个推（Android），用于订单、私信、活动通知。
- **搜索**：MVP 用 MySQL + 前缀索引；P1 引入 Elasticsearch（商品、同袍、攻略全文检索）。

## 6. 环境与配置

| 环境 | 用途 | 域名 |
|------|------|------|
| dev | 本地开发 | localhost |
| test | 联调测试 | *.test.hytp.com |
| prod | 生产 | *.hytp.com |

- 敏感配置（DB 密码、JWT 密钥、OSS AK、AI 服务密钥）走环境变量 / `common/config/*-local.php`，**不入库、不进 git**。
- Android 端 `BuildConfig` 区分 `debug`/`release` 的 baseUrl（见 04）。
